Scooter Challenge: Operator Choice in Real Time

A field-level research tool for micromobility riders in shared-scooter cities.

The problem

Most riders don't know which operator is actually cheaper for them. They see per-minute rates or monthly passes, but their real cost depends on how often they ride, how long their rides are, and whether vehicles are actually available in their neighborhood.

This happens in a gap: operators market their pricing confidently, but riders have no way to compare real costs against their own behavior. That gap costs people $50–150/month in invisible choices.

Example: a real rider's situation
  • Location: East Columbus, near Ohio State University
  • Riding pattern: ~25 rides/month (mix of commute + leisure)
  • Average ride: 13–15 minutes
  • Current operator: Spin (99¢ Club)
  • The question: Should I switch to Veo, or stay on Spin?

The math

Operator A — Spin 99¢ Club

  • Monthly fee: $0.99
  • Per-ride flat: $2.39
  • Speed advantage: 18–22 mph (shorter ride times)

Cost at 25 rides/month: $0.99 + (25 × $2.39) = $60.74

Operator B — Veo VeoPlus Premium

  • Monthly fee: $5.99
  • Per-minute rate: $0.475
  • Speed cap: 17 mph (slightly longer rides)

Cost at 25 rides/month (13.5 min avg): $5.99 + (25 × 13.5 × $0.475) = $166.31

The difference

Spin saves $105.57/month, or $1,266.84/year. Annualized on 200+ annual rides, Spin is roughly 2.7x cheaper at this volume.

The density question

Could Veo's 1.73x fleet advantage offset the cost? If Veo saved 8+ minutes per ride through better availability:

  • 8 min saved × 25 rides = 200 min saved
  • At $0.475/min, that's ~$95 in avoided per-minute charges
  • Veo cost would drop to ~$71 — still more than Spin at $61

Reality check: in the neighborhood, both operators have 100% availability right now. The density advantage exists, but it's not translating to search-time savings. The immediate area is well-served by both fleets.

What the rider decided

Stay on Spin 99¢ Club

Cost advantage is massive ($50–110/month) at this actual volume. Fleet density difference (1.3–2.0x locally) doesn't create enough availability win to offset the per-minute premium. Spin's speed advantage (18–22 mph) compounds the cost win by keeping ride times shorter. The neighborhood has balanced coverage, not a coverage desert.

Contingency: Keep Veo installed as a backup for edge cases (Spin outage, maintenance window, specific destination). But Spin is primary.

What this revealed

This wasn't just a personal decision. It's a case study in how pricing structure matters more than marketing claims.

Key finding: if you ride 20–30 times/month at 10–15 minutes per ride, pricing model (flat vs. per-minute) is the variable that matters. Everything else — brand, fleet size, speed cap — is secondary.

For a rider who uses each operator once a month, or rides for 3–5 minutes at a time, the math would flip. For someone commuting daily on 25+ minute rides, per-minute could win. But for the bulk of casual-to-regular riders in mid-density neighborhoods, flat-rate pricing is unbeatable.

Building Scooter Challenge around this

This analysis turned into a tool so other riders don't have to do this manually. It's live now — linked from the dashboard's main nav, homepage promo card, and Research Library, opening as a mobile-sized popup window on desktop and full navigation on mobile.

The form

  • Your home + up to 3 frequent destinations
  • 2–3 ride receipts — type them in, or scan a screenshot and let it auto-fill the fields (client-side OCR, nothing uploaded; you still review and can correct before submitting)
  • Monthly frequency estimate

The output

  • Live vehicle counts from each location — not hunt time. Hunt time is computed in the codebase but not wired into the live flow yet, so vehicle count remains the actual MVP signal, as originally planned
  • Cost projection at your volume, with a "what does this mean?" explainer on the confidence score
  • Recommendation + confidence score
  • Downloadable skill (Markdown, for Claude/ChatGPT/Gemini) and a raw JSON results snapshot
  • A ticker of real anonymized submissions from other riders, pulled back from PostHog every 6 hours by a scheduled job — honest caveat: it's showing zero real submissions so far, which is itself the current open question

The hypothesis being tested is unchanged: "Riders making operator choices with real data — their own receipts + live fleet density — will make different choices than riders deciding based on marketing." There's no usage data yet to test it. The tool just shipped.

Technical approach

Data sources

  • GBFS feeds: Spin (mds.bird.co provider feed) and Veo (cluster-prod.veoride.com free_bike_status feed) — both free-floating, no station IDs. The original Veo endpoint was wrong (station-based), caught during code review before shipping.
  • Ride history: manual entry, or scan a receipt screenshot — OCR, client-side, no server round-trip
  • Geographic: Haversine distance, ~¼-mile radius for "nearby"

Stack

  • React + Tailwind frontend, using the dashboard's existing light editorial theme (paper / ink / brick / river, IBM Plex + Newsreader) with real operator brand colors sampled from each vendor's site — not the portfolio's dark-ops system originally planned. It ships as part of the public dashboard, so it inherits that visual identity instead.
  • Client-side cost calculation, no backend
  • Client-side OCR (Tesseract.js / WebAssembly) for receipt screenshots
  • Markdown + JSON export for skill reusability
  • Anonymized PostHog + GA4 event on each run, pulled back into a static ticker file by a scheduled GitHub Action — the closest thing to a "backend" this has, and even that never touches raw ride data
  • An admin-only, unlinked page for updating Spin/Veo rates without touching code

Status vs. original timeline

The Aug 1–7 phase plan mostly held: form, calculator, confidence scoring, GBFS integration, results UI, and skill export all shipped within that window. What wasn't originally planned and got added: the admin rates page, anonymized analytics with a real ticker, and OCR — moved up from "next phase" into MVP once client-side OCR turned out to be reasonable.

Success metrics

Still open, since real usage is the missing piece:

  • ✓ Form accepts addresses + receipts without friction
  • ✓ Cost projection matches manual math — verified against this case study: Spin $60.74 vs. Veo $166.31 at 25 rides/mo, 13.5 min avg
  • ✓ Skill export works — Markdown and JSON both shipped
  • – Recommendation aligns with actual rider behavior — no usage data yet
  • – Real submissions — ticker is live but empty; this is the actual current bottleneck, not the build

Broader context

This fits into larger ops/systems work:

  • Operational: field-level decision-making with real data
  • Systems: how information gaps create invisible costs
  • Civic: riders deserve to know what they're actually spending

After three years running mobility operations (Spin, Veo), building dashboards that make fleets legible, publishing field reports — this tool extends that work into the rider's perspective.

The north star is the same: how do you build systems where people feel safe, seen, and able to move forward? Part of that is transparency about cost.

Working notes

Unanswered questions

  • Does Veo's 1.73x fleet actually feel different to riders, or is 1.3–2.0x local density below the perceptual threshold?
  • If you switched operators and tracked 50 rides, would real-world costs match projections?
  • How does vehicle condition (battery, cleanliness) factor into the choice? Still doesn't — and for Veo specifically, it can't: I confirmed while building fleet-movement tracking that Veo's GBFS feed never reports a battery percentage at all, across every archived snapshot. Range remaining is the closest proxy Veo exposes.

Data gaps

  • Only 3 recent ride receipts informing this specific case study; would be better with 20+
  • No Veo ride data from this location
  • GBFS snapshots were ~11 min apart for this analysis — but the pipeline now pulls twice daily (8am / 8pm UTC) plus an on-demand fleet export, so density data going forward is less of a single-moment snapshot than it was when this was first drafted

Design constraints

  • MVP won't include OCR — it does now
  • – No geocoding API — still true, addresses / lat-lon are manual entry
  • – Client-side only, no persistent storage of your ride history — still true; what changed is that an anonymized, aggregated usage event is now logged per run, never your address or receipt amounts
